# GoldHEN 14.02 port status (2026-11-11)

GoldHEN launch on 14.02 remains disabled. A console run of the first reconstructed
candidate ended in a hardware kernel panic. Later controlled diagnostics
established the browser and device prerequisites and completed three 14.02
kernel reads without a panic. GoldHEN and kernel writes remain untested by
those successful diagnostics.

## Supplied HEN and offsets files

The current project includes the user's `hen.bin` and `offsets-1402.json` in
`site/` so both files are preserved with the project assets. Their SHA-256
values are recorded below. The current launch gate still stops the 14.02
GoldHEN path before the kernel stage; neither file is wired into that path.
The JSON is a reference artifact and does not override
`site/ps4_offsets.js`.

The latest [GoldHEN beta from SiSTRo](https://ko-fi.com/s/e694c36022) adds

lists 14.02 as upcoming. No authenticated 14.02 GoldHEN release is used here.

## What the supplied archive provides

The archive contains browser exploit source and compiled payloads. It does not
contain matching buildable GoldHEN C source or a pristine decrypted 14.02
kernel. The corrected local GoldHEN candidate is reproducible from those
compiled inputs, but remains unverified on hardware and is not deployed.

The available `kernel_1402.bin` reference is unsuitable as a clean stock
image: six bootstrap windows already have final bytes, one remains stock,
two syscall fields are zeroed, and the fifteen host patch windows are mixed
(fourteen stock, one final). The offline classifier in
`site/preflight-1402.js` rejects this state.

An independent [ps4debug-NG 14.02 patch table](https://github.com/Pharaoh2k/ps4debug-NG/blob/main/installer/source/installer.c)
and [kernel function guards](https://github.com/Pharaoh2k/ps4debug-NG/blob/main/ps4-ksdk/source/ksdk.c)
provide a limited cross-check. All 17 retail patch windows and 21 function
prologues sampled from that project match the reference ELF's text. This
corroborates those 38 locations, not the complete image or hardware behavior.
The ELF has no section headers, its dynamic segment is zero, and the entire
segment containing `sysent` is zero. It cannot recover the 18 original syscall
records or ten handler targets required to guard GoldHEN's writes. A separate
live read on the user's 14.02 PS4 has now recovered these selected values.

A read-only capture through the debugger already running on the user's 14.00
console supplied its 13,625,472-byte executable kernel segment (SHA-256
`eb90a16d40d0ff9c9fe6d28919aa731aee347dac74510a94a25233612f74c284`).
An independent instruction-level comparison against the available 14.02 text
found matching logic across 36,423 instructions in the APM driver, device
lifecycle, kqueue, and devfs regions. Relative branch and call targets move
with the surrounding code; checked constants and structure offsets match.
The APM close path and its device-destruction helpers also match. This is
evidence against a direct fix in those visible code paths, but it does not
prove the exploit works: the 14.02 image has incomplete data, other paths may
have changed, the 14.00 capture includes live payload patches, and the earlier
panic has no stage marker.

The user's `PS4UPDATE.PUP` is the retail 14.02 system update: its MD5
`2acc318d7cafb18d7898754c8a97e2da` matches [Sony's current update URL](https://pc.ps4.update.playstation.net/update/ps4/image/2026_1023/sys_2acc318d7cafb18d7898754c8a97e2da/PS4UPDATE.PUP).
Its SHA-256 is `7bbe52c4fed78066f32ada246af16908cfb49ced76978bae5bd5e54e2ca69f9a`.
It is a two-part encrypted SLB2 container. The user's 14.00 GoldHEN console
successfully ran the [PupDecrypt-PS4](https://github.com/iHaiDeeZ/PupDecrypt-PS4)
payload and produced both outer-decrypted PUP fragments. Their segment tables
are readable, both report firmware `0x14020000` (14.02), and their file sizes
match the two outer SLB2 entries. The [PUP format](https://www.psdevwiki.com/ps4/PUP)
and [SLB2 format](https://www.psdevwiki.com/ps4/SLB2) identify segment ID 5 as
CoreOS and its `80010002` member as the host kernel SELF. The extracted files
are in local analysis storage outside this repository:

| `80010002.self` (kernel) | 10,868,386 | `04d8d9068533c944dfaa72daecd91d8fc68a33485931903d4394d28356b398d0` |

The kernel SELF identifies program type `0x0c` (host kernel) and requests
firmware 14.02 (`0x0000140200000000`). Its single segment has flags `0x40f`:
it is signed, encrypted, and compressed. The encrypted segment is 10,867,620
bytes; its declared decrypted size is 21,653,136 bytes. Header key type
`0x0c` identifies the kernel class, not a separately readable key revision.
The [SELF format and decrypter notes](https://www.psdevwiki.com/ps4/SELF_-_SPRX)
state that a console-based SELF decrypt normally requires the SELF's minimum
firmware to be below the console's installed firmware. The 14.02 kernel SELF
therefore does not meet that condition on the 14.00 console. No 14.00 SELF
decryption or key compatibility has been demonstrated; version spoofing alone
is not evidence that the secure-module check or key requirements can be met.
The PUP still cannot provide its stock RELRO and `sysent` data directly.
The original PUP and extracted firmware files are kept off the public site and
GitHub.

## Offline work in this repository

- `site/preflight-1402.js` classifies supplied kernel bytes as stock, final,
  mixed, or unknown. It has no live kernel reader and no launch path.
- `tools/check-1402-snapshot.cjs` runs that classifier on a local raw image.
- `tools/build-guarded-bootstrap-1402.cjs` generates an offline bootstrap
  prototype that checks fifteen bootstrap/syscall sites before its intended
  writes. It orders syscall 11 activation last and rollback deactivation
  first. No published page imports or executes this prototype.
- `site/teardown-verify-1402.js` checks a supplied snapshot of both complete
  cloned operation tables, all device and queue file pointers, and queue note
  words. It is not connected to the live cleanup path.
- `tests/` exercises the classifier and the bootstrap transition order.

The separate [`/u1/` browser check](14.02-browser-only-probe.md) is a
userland-only diagnostic. A 14.02 console run on 2026-11-11 established the
WebKit memory primitive on its third attempt and passed all 15 browser gadget
and 24 libkernel syscall-stub checks. It stopped before any ROP syscall or
kernel stage. This narrows the earlier panic to a later part of the chain but
does not identify that part or prove GoldHEN compatibility. The safe `/d1/`
page links to the check with an explicit Start button.

The separate [`/u2/` device check](14.02-device-probe.md) can test ROP native
calls, APM clone access, CPU affinity, and socket setup without firing
the UAF or loading GoldHEN. It requires a button press and records an honest
PASS or BLOCKED result. A 14.02 hardware run reached native ROP, opened 20
APM clones, restored CPU affinity, and created all 126 UDP sockets. Its
0/126 socket-option result came from invalid repeat calls. A corrected second
run returned 0 from a fresh exact-request option call and from the last call
of each timed batch. This confirms option acceptance but does not establish
that the kernel spray or UAF works on 14.02.
A cold reboot is required after this check before any later exploit attempt.

An isolated, locally served 14.02 snapshot diagnostic then completed three
APM use-after-free read shots on the console. It saved 18 original, complete
`sysent` records and ten 14-byte handler prologues to the user's PC outside
this repository. Both partial and full files pass schema and checksum checks;
the selected original syscall 11 fields and all ten handler prologues match
independent 14.02 expectations. This is direct evidence that the APM read ROP
worked on one boot. It did not test kernel writes, bootstrap, gate creation,
handle teardown, or GoldHEN. The console was fully powered off afterward.
The snapshot files remain private and are not published to GitHub.

A second local, read-only check on a fresh 14.02 boot also completed all three
APM read shots without a panic. The PC saved the complete 28,416-byte table of
592 syscall entries, ten handler prologues, fifteen host patch windows, seven
bootstrap windows, and a 4 KiB gadget scan. The selected 18 syscall records
and ten handler prologues matched the prior snapshot; every host patch window
was stock. Across all 592 entries, each of the ten planned handler caves had
exactly its intended syscall owner and no other alias. The scan found exactly
one `xchg rbp, rax; ret` at RVA `0xa81478`. All captures remain private, and
the console was fully powered off afterward. This still made no kernel patch,
bootstrap call, gate, cleanup, or GoldHEN launch.

A later private thread/process diagnostic stopped safely after its first APM
shot returned without a valid kernel-base leak. It made no further kernel
reads. On the next fresh boot, the same diagnostic completed six read shots.
The PC confirmed the stock syscall table, host and bootstrap windows, unique
live swap gadget, and exact `gs:[0]` gadget bytes before following any new
pointer. The kernel thread ID matched the browser's thread ID; the kernel
process ID matched its process ID. File-descriptor and VM-space pointers were
recorded as candidates but were not followed. The console was fully powered
off after each run. These results do not establish a safe kernel write,
bootstrap, cleanup path, or GoldHEN launch. The captures and dynamic pointers
remain private.

Separate browser-only checks on fresh 14.02 boots confirmed the host memory
region is readable and executable and that the browser can open `/dev/rng`.
Both available file-listing queries returned `ENOENT` on the retail browser,
so they did not reveal the live kernel file pointer. These checks made no
kernel exploit shot or GoldHEN attempt. Their captures remain private.

The seven live bootstrap windows were stock. Two branch displacements were
different from our earlier reconstruction: the full windows at `0x4b5` and
`0x4b9` are `721385c9750f483b` and `750f483b90f00000`. Both branches
target `0x4ca`; the old guessed values targeted four bytes earlier. The
offline classifier and guarded bootstrap prototype now use the live bytes.
They remain disconnected from the disabled 14.02 launch path.

The 14.02 reference text has one `xchg rbp, rax; ret` gadget in the host's
4 KiB scan window at RVA `0xa81478`. The inherited 14.00 RVA `0xa80f68` is
not a gadget on 14.02. The inactive 14.02 launch path now stops if the live
scan misses or finds multiple matches instead of falling through to the
14.00 address. This guard prevents one known panic path; the later dynamic
pointer walk, kernel writes, bootstrap response, and handle cleanup still
need staged checks before launch is enabled.

The fixed-site bootstrap guard does not cover the exploit's earlier dynamic
writes to VM mapping rights and a file operation pointer. Those writes and
the UAF handle state are described in the
[offline kernel diagnostic design](14.02-kernel-diagnostic-design.md).

The offline bootstrap is not ready for console use. The current host ignores
the bootstrap ioctl result, can overwrite the bootstrap with scratch code
before handling a refusal, and does not fully verify cleanup of every device
and queue handle. Cross-core kernel text updates also need review.

## Remaining launch requirements

1. Integrate the captured syscall, handler, host, and bootstrap stock guards
   into a same-boot launch preflight. Verify all remaining loader, GoldHEN core,
   and dynamic write sites before any kernel write. The supplied reference
   still zeroes its data segment.
2. Guard and verify the loader and GoldHEN core writes in separate phases.
   The compiled candidate has 63 logical fixed write targets, including
   seven complete syscall entries and ten dynamically resolved handlers.
3. Integrate the bootstrap with explicit refusal handling, full cleanup
   verification, and diagnostic checkpoints. Review the machine code and
   failure paths independently.
4. Perform a controlled kernel-only test and cleanup before attempting a
   GoldHEN thread. Keep the 14.02 launch disabled until those checks pass.

Local offline checks:

```sh
node tests/preflight-1402-selftest.cjs
node tests/guarded-bootstrap-1402-selftest.cjs
node tests/teardown-verify-1402-selftest.cjs
```
